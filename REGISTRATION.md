# Signed registration (protocol v1)

> Read [`../DESIGN_PRINCIPLES.md`](../DESIGN_PRINCIPLES.md) first. Every rule
> below follows it: events, not timers; no retries; no timeouts as a fix;
> strict ordering; §1's 5 seconds.

**Status:** specification, 2026-10-03. Not implemented. Reticulum-post `main`
at 3281ad5, the wildcard hotfix, is live on both relays.

**Normative for:**

- Reticulum-post (PHP relay): `registerInterface()`, the new endpoints, the
  schema, the announce guard, and PHP-to-PHP peering.
- Retichat-js (browser): `lib/rns/interfaces/post_interface.js`.
- Reticulum-rust `PostInterface` (gateway), and the Python
  `RNS/Interfaces/PostInterface.py` in this repository.

**Byte-exact vectors:** [`php/tests/vectors/registration_vectors.json`](php/tests/vectors/registration_vectors.json),
generated by [`tools/registration_vectors.py`](tools/registration_vectors.py)
from RNS 1.5.2 and checked independently by
[`tools/check_registration_vectors.php`](tools/check_registration_vectors.php).
If this text and the vectors ever disagree, that is a bug. Fix the text and
regenerate the vectors in the same commit.

MUST, MUST NOT, SHOULD and MAY carry their RFC 2119 meanings.

## 0. Why

Before this change, `POST /v1/interfaces/register` took ownership claims on
trust. The design pass (workflow wf_73a89cca-022) proved these attacks against
the real trait:

| # | Attack | Evidence | Closed by |
|---|---|---|---|
| A1 | Re-bind any browser row by POSTing its `identity_hash`, which any `lxmf.delivery` announce reveals. The same `interface_id` comes back, the victim's token is rotated so its next exchange gets 401, and the metadata is overwritten (mode set to 6). | `rebind_probe.php` on 35314f4 | §2–§4, §7 |
| A2 | `identity_hash = '%'` or `'_%'` was a LIKE wildcard that re-bound an arbitrary browser row with no knowledge at all. | same probe; hotfix 3281ad5 (live) | hotfix; §7 removes the metadata lookup |
| A3 | Interception with no re-bind: register your own identity, then replay a victim's signed announce through your row. The victim's `local_destinations` binding moves to you (endpoint→endpoint overwrite), and a third party's DATA to the victim is queued to you. | `probe2/announce_replay_probe.py` on a real `php -S` node at 35314f4 | §8 |
| A4 | An `rns-js` row in mode 3/5/6 skips the local-binding code entirely. `upsertPathFromAnnounce`'s `shorter_path_replaced` branch accepts an announce whose random blob it has already seen when the unsigned hop count is lower, so a replay with hops set to 0 pulls the path to any destination 2 or more hops away. | code reading at 35314f4 (not probed) | §8 |
| A5 | Any `client = reticulum-php` registration re-binds the row whose `peer_url` matches the claim (or the claim ± `/v1/wake`). That includes the relay's own initiator row for a PHP peer and the production gateway's wake-mode row (8d2a523d, mode 6, `peer_url http://jrl290.ddns.net`). | design map, lane 2 | §9, §10 |
| A6 | During any transition, an unsigned row with a made-up claim replays a victim's announces (A3 through a legacy row). | critique | §8 (from Phase 1) |
| A7 | The first signed registration inherits an attacker's squatted row, with its bindings, paths, links and queued batches. | critique | §4.5 |
| A8 | Identity claims reach rows through other client strings (`rns-post-interface`, `reticulum-php` that falls through). | critique | §7 |

What a captured row gave an attacker: the session (eviction and DoS, repeatable),
delivery of the victim's inbound packets (payloads stay end-to-end encrypted,
but delivery is denied and link metadata is exposed), path next-hop
capture, and the row's mode and metadata.

## 1. Who proves what

| Registrant | `client` | Proof | Row key |
|---|---|---|---|
| Browser (Retichat-js) | `rns-js` | Ed25519 signature by its RNS identity over a relay challenge (§2–§3) | `identity_hash` |
| Gateway, wake mode (Reticulum-rust / Python `PostInterface`) | `reticulum-php` | Signature by its **persistent transport identity** (§9) | `identity_hash` |
| Gateway, poll mode | `rns-post-interface` | Same signature | `identity_hash` |
| PHP relay peer (Reticulum-post `connectToPeer`) | `reticulum-php` | One-time nonce confirmed at the peer's own HTTPS URL (§10) | normalised `peer_url` |

The identity hash is self-certifying. RNS 1.5.2 defines it as
`identity_hash = SHA-256(x25519_pub(32) || ed25519_pub(32))[:16]`
(`RNS/Identity.py` `get_public_key`, `update_hashes`; `TRUNCATED_HASHLENGTH = 128`).
The relay recomputes it from the 64-byte public key in the registration, so
there is no PKI, no pin, no trust-on-first-use and nothing to configure.

Every interface row carries a `registration_proof`:

| Value | Meaning |
|---|---|
| `none` | Legacy. Nothing was proven. Only possible while `enforce_signed_registration` is false. |
| `signed` | Bound by a verified signed registration. The row has `identity_hash`, `identity_public_key` and `registration_seq`. |
| `confirmed` | A PHP peer row bound after a successful `/v1/peers/confirm` (§10). |
| `local` | A PHP peer row this relay created itself in `connectToPeer`, toward a URL from its own config. |

## 2. The challenge

James's decision: "a standard challenge and signing". It is stateless. The
relay keeps no nonce table, sets no TTL and runs no sweep.

### 2.1 Endpoint

```
POST /v1/interfaces/challenge          {"public_key": "<128 hex>"}
POST /v1/interfaces/challenge          {"identity_hash": "<32 hex>"}
GET  /v1/interfaces/challenge?public_key=<128 hex>
GET  /v1/interfaces/challenge?identity_hash=<32 hex>
```

Exactly one of `public_key` or `identity_hash` MUST be given, as lower-case
hex. Anything else gets `400 {"error":"bad_challenge_request"}`. Clients MUST
use POST. GET exists for operators. The relay MUST send `Cache-Control:
no-store` on both, because a cached challenge would turn into two `409`s
(§6). The response is:

```json
{
  "status": "challenge",
  "version": 1,
  "identity_hash": "<32 hex>",
  "registration_seq": 0,
  "challenge": "<112 hex = 56 bytes>"
}
```

`registration_seq` repeats the value inside the challenge for diagnostics.
Clients MUST NOT use it for anything else.

### 2.2 Bytes

```
H          = the identity hash (16 bytes), from public_key or as given
seq        = registration_seq of the row whose identity_hash = H, or 0 if there is none
nonce      = 16 random bytes (CSPRNG)
mac        = HMAC-SHA256(relay_secret, "reticulum-post/challenge/v1" || H || u64be(seq) || nonce)
challenge  = nonce(16) || u64be(seq)(8) || mac(32)                      -- 56 bytes
```

The domain string is the 27 ASCII bytes `reticulum-post/challenge/v1`. Every
other part of the MAC input has a fixed width, so the concatenation is
unambiguous. `u64be` is an unsigned 64-bit big-endian integer.
`seq` MUST be below 2^53 − 1, the JavaScript safe-integer limit. A relay never
issues or accepts anything larger, and no row will ever reach it.

### 2.3 `relay_secret`

- 32 random bytes, generated on first use and stored as hex in
  `transport_state` under `state_key = 'registration_challenge_secret_hex'`.
  To create it, the relay does INSERT-or-ignore and then SELECT, so concurrent
  first requests end up with the same value.
- It MUST never appear in `/health`, `/debug`, `/v1/monitor*`, logs or
  responses.
- Any database reset rotates it. `clearAllData()` already empties
  `transport_state`. When it rotates, every outstanding challenge dies. That is
  intended.
- Because the MAC is keyed by this relay's own secret, a challenge (and any
  signature over it) from one relay can never be used at another. **The
  client therefore does not sign the relay's URL.** There is no audience
  string, so there is no exchange-URL normalisation to get wrong (the critique
  found that trailing-slash, `www`, scheme or saved-URL differences would have
  been an outage).

### 2.4 Single use comes from `seq`

A successful signed registration moves the row from `seq` to `seq + 1`
atomically (§4.4). Every challenge that carries the old `seq` then fails §4.3
step 6, permanently. A captured signed body therefore works at most once, and
since the session token comes back encrypted to the identity (§5), the one
who replays it gets nothing usable.

A challenge that is never used stays valid until the row's `seq` moves or the
secret rotates. That is harmless: using it needs the identity's private key,
and using it consumes it.

### 2.5 Old relays

A relay that predates this spec answers the challenge endpoint with `404`.
That is the only signal a client uses to fall back to the legacy unsigned
registration (§11.4). Clients MUST NOT fall back on any other status.

## 3. Signed bytes

```
lp(x)  = u16be(len(x)) || x                (len(x) ≤ 65535)

signed = lp("reticulum-post/register/v1")            -- 26 bytes, lp = 001a…
      || lp(challenge)                               -- 56 bytes, exactly as received
      || lp(public_key)                              -- 64 bytes: x25519_pub || ed25519_pub
      || lp(utf8(name))
      || lp(u64be(bitrate))
      || lp(u32be(mtu))
      || lp(utf8(metadata.client))
      || lp(u8(metadata.mode))
      || lp(utf8(metadata.transport          or ""))
      || lp(utf8(metadata.peer_url           or ""))
      || lp(utf8(metadata.peer_interface_id  or ""))
      || lp(utf8(metadata.peer_session_token or ""))

signature = Ed25519-sign(ed25519_private_key, signed)  -- RNS Identity.sign, 64 bytes
```

There is one layout, with twelve fields, for every registrant. A browser
signs the four optional fields as empty strings. A wake-mode gateway fills in
the three `peer_*` fields. A poll-mode gateway fills in `transport`. No JSON
appears in the signed bytes: PHP's `json_encode` escapes `/` and the other
encoders do not.

Rules for reading the values:

1. The values MUST be read from the decoded JSON body **before any
   normalisation**: no trimming, no case folding, no URL rewriting. The relay
   normalises only after verification, for storage and lookup.
2. `name`: a non-empty JSON string of valid Unicode (no lone surrogates),
   ≤ 255 bytes as UTF-8.
3. `bitrate`: a JSON integer, 1 … 2^53 − 1. `mtu`: a JSON integer,
   1 … 2^32 − 1. `mode`: a JSON integer, 1 … 7 (the RNS interface modes).
   Strings and floats such as `1e6` are refused.
4. `client`: a non-empty string of ≤ 64 bytes. `transport` ≤ 64 bytes,
   `peer_url` ≤ 512, `peer_interface_id` ≤ 64, `peer_session_token` ≤ 128 (the
   column widths). A key that is absent, `null`, or `""` encodes as `lp("")`
   (`0000`) and is stored as absent.
5. `challenge`, `public_key` and `signature` are lower-case hex of exactly
   112, 128 and 128 characters.

Why each field is covered: `challenge` gives freshness and binds the relay;
`public_key` is what is proven; `name`, `bitrate`, `mtu`, `client`, `mode` and
`transport` change how the relay treats the row; the `peer_*` fields are where
the relay sends wakes and what it presents when it calls back. Nobody can alter
any of them without the key.

**The domain tag cannot collide with RNS signatures.** RNS announce, link,
proof and LXMF signatures sign raw protocol bytes that start with a 16- or
32-byte hash or key. For an RNS-signed blob to begin with `lp("reticulum-post/register/v1")`,
a destination hash would have to equal those 16 bytes, which is a 128-bit
preimage. The critique also checked every other signature the browser makes
(`app.js` 5681, 5970, 5998, 6503), and none can start with the tag.
Implementations MUST build these bytes in a single function
(`signRegistration()` in the browser) and MUST NOT sign bytes received from the
network.

## 4. Registering

### 4.1 Request

```json
POST /v1/interfaces/register
{
  "name": "Retichat Web",
  "bitrate": 1000000,
  "mtu": 500,
  "metadata": { "client": "rns-js", "implementation": "PostInterface", "mode": 1 },
  "registration": {
    "version": 1,
    "public_key": "<128 hex>",
    "challenge":  "<112 hex, verbatim from §2.1>",
    "signature":  "<128 hex>"
  }
}
```

`registration` is a new top-level key, so a relay that predates this spec
ignores it, and it never reaches `metadata_json`. The `registration` object
MUST hold exactly those four keys, and `version` MUST be `1`.

**In a signed registration the metadata keys are limited** to the signed ones
(`client`, `mode`, `transport`, `peer_url`, `peer_interface_id`,
`peer_session_token`) plus two more:

- `implementation`: informational, ≤ 64 bytes. The relay never bases a
  decision on it.
- `identity_hash`: optional. If present it MUST equal the identity hash derived
  from the key (otherwise `400 identity_hash_mismatch`), and it is never stored.

Any other key gets `400 unsigned_metadata`. The relay MUST never act on a value
the signature does not cover. A new field means a new layout (v2), not an
unsigned key. `wake_url` and `ifac_*` are therefore not available to signed
registrations in v1. No signing client sends them today.

### 4.2 Which path

| Body | Path |
|---|---|
| has `registration` | **signed** (§4.3), whatever `client` says |
| no `registration`, `client = reticulum-php`, has top-level `registration_nonce` | **peer-confirmed** (§10.2) |
| has both `registration` and `registration_nonce` | `400 bad_registration` |
| anything else | **legacy** (§7.2): accepted only while `enforce_signed_registration = false` |

### 4.3 Verifying a signed registration

The relay runs these checks in this order. The cheap ones come before the
Ed25519 verification, and nothing is written to the database before step 8.

| Step | Check | On failure |
|---|---|---|
| 1 | Shape: §3 rules 2–5, §4.1 `registration` object | `400 bad_registration` |
| 2 | Metadata keys within the signed set (§4.1) | `400 unsigned_metadata` |
| 3 | `H = SHA-256(public_key)[:16]`; `metadata.identity_hash`, if present, equals `H` | `400 identity_hash_mismatch` |
| 4 | Client policy: `client = rns-js` with `mode ∈ {3, 5, 6}` | `400 transit_mode_not_allowed` |
| 5 | Split the challenge into `nonce`, `seq`, `mac`; recompute the MAC (§2.2) over **the derived `H`**; compare in constant time | `409 stale_challenge` |
| 6 | `seq` equals the current `registration_seq` of the row with `identity_hash = H` (0 if there is none) | `409 stale_challenge` |
| 7 | `sodium_crypto_sign_verify_detached(signature, signed, public_key[32:64])` over bytes rebuilt from the received body (§3) | `403 bad_registration_signature` |
| 8 | Atomic bind (§4.4) | `409 stale_challenge` |

Each negative vector fails exactly one of these steps, so an implementation
that orders them differently still gives the same answers. The order above is
still the one implementations MUST use, because it is the cheapest.

### 4.4 Binding atomically

The row is looked up only by `identity_hash = :H`, an exact match on its own
column, which has a UNIQUE index (§12).

- **`seq = 0` (no signed row):** `INSERT` a new row with
  `interface_id = random 16 bytes hex`, `identity_hash = H`,
  `identity_public_key = public_key`, `registration_seq = 1`,
  `registration_proof = 'signed'` and the signed parameters. A
  unique-constraint conflict means another registration for `H` won: the relay
  looks the row up again (only to log it) and answers `409 stale_challenge`. It
  does not insert a second time.
- **`seq > 0`:** update in place.

  ```sql
  UPDATE interfaces
     SET session_token = :token, name = :name, bitrate = :bitrate, mtu = :mtu,
         status = :online, metadata_json = :metadata_json, last_seen_at = :now,
         updated_at = :now, registration_seq = :next_seq,
         peer_url = :peer_url, peer_interface_id = :peer_interface_id,
         peer_session_token = :peer_session_token
   WHERE identity_hash = :h AND registration_seq = :seq AND identity_public_key = :pub
  ```

  `rowCount() = 1` is required, otherwise `409 stale_challenge`. The statement
  always changes `registration_seq` and `session_token`, so MySQL's
  "affected rows" equals "matched rows". No `PDO::MYSQL_ATTR_FOUND_ROWS` is
  needed.

The interface keeps its `interface_id` across re-registrations, so its queue,
paths and links survive a re-registration and, for the gateway, a restart.

### 4.5 A signed registration never adopts a squatted row

The legacy path keeps its claims in `claimed_identity_hash`, never in
`identity_hash` (§7). A signed registration therefore can never land on a
legacy row. After every successful signed bind for `H` (the INSERT, and
also the UPDATE, which catches a legacy row that raced in between), the
relay **retires** every row with `claimed_identity_hash = H` and
`registration_proof = 'none'`. When there is none, that costs one indexed
`SELECT`. For each
one it deletes, in this order: `local_destinations`, `path_entries`,
`reverse_path_entries` and `link_transport_entries` (matching
`received_interface_id` or `outbound_interface_id`), `outbound_packets`,
`outbound_batches`, `wake_events`, and then the `interfaces` row. It logs
`[REG-RETIRE] identity=<H> rows=<n>`.

The holder of a retired row, whether the user's own stale tab or a squatter,
gets `401` on its next exchange. If it then re-registers unsigned while
claiming `H`, it gets `403 identity_requires_signature` (§7.2).

Packets queued to a retired row are dropped. They were queued to a row whose
owner was never proven, so handing them to the proven identity is exactly the
adoption the critique ruled out (A7).

### 4.6 What is stored

- **Columns:** `identity_hash`, `identity_public_key`, `registration_seq`,
  `registration_proof`; the signed `peer_*` fields in their existing columns,
  with `peer_url` normalised (§10.1); and `name`, `bitrate`, `mtu`.
- **`metadata_json`:** only `client`, `implementation`, `mode` and
  `transport`.
- **Never in `metadata_json`, on any path:** `identity_hash`,
  `identity_public_key`, `registration_seq`, `registration_sig`, the
  `registration` object, or `registration_nonce`.

The relay strips these before every write. That leaves nothing for a LIKE (or
any other metadata lookup) to match (A2, A8).

## 5. The response: the token comes back encrypted

A signed registration is answered **only** like this:

```json
{
  "status": "registered",
  "interface_id": "<32 hex>",
  "identity_hash": "<32 hex, the relay's derived H>",
  "registration_seq": 1,
  "session_token_encrypted": "<hex>",
  "idle_exchange_interval_ms": 1000,
  "max_batch_packets": 64,
  "max_packet_bytes": 500
}
```

It MUST NOT contain `session_token`, `peer_interface_id` or
`peer_session_token`. A test MUST assert this. The last three fields are
today's operational fields, unchanged. The session token is a fresh
`bin2hex(random_bytes(32))`, the same as today.

`session_token_encrypted` is RNS `Identity.encrypt(utf8(session_token))` to the
registrant's public key, with no ratchet:

```
eph        = fresh X25519 key pair
shared     = X25519(eph_private, public_key[0:32])
derived    = HKDF-SHA256(ikm = shared, salt = H, info = "", L = 64)
hmac_key   = derived[0:32]      aes_key = derived[32:64]
iv         = 16 random bytes
ct         = AES-256-CBC(aes_key, iv, PKCS7(utf8(session_token)))
blob       = eph_public(32) || iv(16) || ct || HMAC-SHA256(hmac_key, iv || ct)(32)
```

For a 64-character token the blob is 160 bytes (320 hex). This is the
derivation `request_lxmf_handoff_trait.php` already implements
(`buildOutboundSinglePacket` / `encryptIdentityToken`). The salt is the
registrant's **identity** hash.

The client decrypts with its identity, using RNS `Identity.decrypt`, the web
`Identity.decrypt` or Rust `Identity::decrypt`. Then:

- the plaintext MUST be 64 lower-case hex characters, and that string is the
  session token;
- `identity_hash` in the response MUST equal the client's own hash.

If either fails (including an HMAC failure), it is a protocol error: the
client stops and shows it (§6). It never falls back to a plaintext field.

A legacy (unsigned) registration keeps today's response, with a plaintext
`session_token`, until enforcement. A peer-confirmed registration (§10) also
returns a plaintext `session_token`: a PHP peer has no key, and the token
travels over the HTTPS URL that the confirm just proved.

## 6. Errors

Every 4xx body is `{"error": "<code>", "message": "<one line for a person>"}`.
Clients act on the HTTP status and `error` only. **`401` means only "session
lost".** `/v1/interfaces/register` and `/v1/interfaces/challenge` never return
401. Existing clients already re-register on 401, and that stays the one and
only automatic re-registration.

| Status | `error` | Raised when | Client action |
|---|---|---|---|
| 400 | `bad_challenge_request` | challenge request without exactly one well-formed key or hash | stop, show |
| 400 | `bad_registration` | malformed `registration` object or signed field (§3); both `registration` and `registration_nonce` present | stop, show |
| 400 | `unsigned_metadata` | a metadata key outside the signed set (§4.1) | stop, show |
| 400 | `identity_hash_mismatch` | `metadata.identity_hash` ≠ the key's hash | stop, show |
| 400 | `transit_mode_not_allowed` | `rns-js` with mode 3, 5 or 6, signed or legacy (§8) | stop, show |
| 403 | `bad_registration_signature` | signature does not verify | stop, show |
| 409 | `stale_challenge` | MAC is not this relay's for this identity (another relay, a rotated secret, another identity, an altered challenge); `seq` ≠ the row's; or the bind race was lost | **fetch ONE new challenge and register ONCE more**; a second 409 is terminal: stop, show |
| 403 | `identity_requires_signature` | legacy registration claiming an identity that has a `signed` row here | stop, show "reload this page" |
| 403 | `signature_required` | unsigned registration while `enforce_signed_registration = true` | stop, show "reload this page" |
| 400 | `peer_url_not_allowed` | peer registration whose `peer_url` is not `https://` (loopback `http://` only with `allow_loopback_http_peers`) | log, stop |
| 403 | `peer_confirmation_failed` | the confirm call (§10.2) did not answer `200 {"confirmed": true}` | log, stop; the next event re-registers |
| 403 | `peer_confirmation_required` | a legacy peer registration that would re-bind a `local`/`confirmed` row, or any unconfirmed peer registration under enforcement | log, stop |
| 401 | `unauthorized` | `/exchange`, `/tx`, `/poll`, `/goodbye` only: unknown session, or (under enforcement) a `none` row | re-register (signed: challenge, then register), once per run, as today |
| 404 | (any) | challenge endpoint on a relay that predates this spec | legacy registration (§11.4) |

The `409` second step is a documented protocol step with a fixed bound of one,
like a digest-auth challenge. It is not a retry loop (§3 of the principles).
It covers two tabs or devices racing on one identity, and a relay DB reset
landing between challenge and register.

**"Stop, show"** means:

- **Browser:** no further automatic registration. The reason reaches the UI
  through `down`. A reload or an explicit reconnect starts again. The 5-second
  reconnect cadence MUST NOT apply to these codes.
- **Gateway:** an ERROR log line with the code, and no further registration
  until the process restarts.

Network failures and 5xx are not protocol answers. They keep each client's
existing handling, apart from the gateway changes in §9.

Old clients do not know these codes. An old tab treats any non-401 as
"failed" and tries again every 5 s with the error text in its "down" reason,
which is why the `message` for `signature_required` and
`identity_requires_signature` says to reload.

## 7. Re-bind rules

### 7.1 Summary

| Registration | May create | May re-bind |
|---|---|---|
| signed, any `client` | the row for its own derived identity | only that row, through §4.4 |
| peer-confirmed | a URL row (`identity_hash IS NULL`) | the URL row with the same normalised URL and proof `none`, `local` or `confirmed`. Never an identity row |
| legacy `rns-js` (accept-both only) | a row with `claimed_identity_hash = claim`, or with no claim | only a `none` `rns-js` row with the same `claimed_identity_hash`. Never a `signed` row |
| legacy `reticulum-php` (accept-both only) | a URL row with proof `none` | only a URL row with proof `none` |
| legacy, any other `client` (accept-both only) | a new row (no deduplication, as today) | nothing |
| anything unsigned and unconfirmed, under enforcement | nothing | nothing |

Invariants:

- **Identity rows are reachable only through §4.3, whatever `client` says.**
  The only reads of `identity_hash` and `identity_public_key`, and the only
  advance of `registration_seq`, happen in the signed path, apart from the
  read-only checks in §7.2 and §8. No legacy path writes those columns.
- **Every URL lookup excludes identity rows** (`AND identity_hash IS NULL`).
  That covers `phpPeerInterfaceByPeerUrl`, the `/v1/wake` handler's
  `exchangeWithPhpPeer`, `connectToPeer`'s `already_connected` check and
  `ensureConfiguredPeerSessions`. A signed row that names a PHP peer's URL can
  therefore never take over wake lookups. Wake *dispatch* to a signed gateway
  row still uses that row's own `peer_url` column.
- `interfaceByIdentityHash()`, the metadata lookup the hotfix narrowed, is
  deleted. The legacy claim lives in `claimed_identity_hash` (§12).

### 7.2 The legacy path (accept-both only)

Legacy `rns-js`, in order:

1. Mode 3, 5 or 6: `400 transit_mode_not_allowed`.
2. Enforcement on: `403 signature_required`.
3. The claim is `metadata.identity_hash` if it is 32 lower-case hex. A
   malformed claim is no claim, logged `[REG-BAD-IDENTITY]` as today.
4. If a row has `identity_hash = claim`: `403 identity_requires_signature`.
5. If there is a claim and a row with `claimed_identity_hash = claim AND
   registration_proof = 'none' AND identity_hash IS NULL` and `client = rns-js`:
   re-bind it in place, as today, with a plaintext token. Otherwise INSERT with
   `claimed_identity_hash = claim`.
6. Log `[REG-LEGACY] client=rns-js type=browser action=<created|rebound> interface=<id8>`.

Legacy `reticulum-php` with no nonce: under enforcement,
`403 peer_confirmation_required`. Otherwise:

- a URL row with proof `none` is re-bound, as today;
- a URL row with proof `local` or `confirmed` gets `403 peer_confirmation_required`;
- if there is no row, a new one is inserted with proof `none`.

All of these are logged `[REG-LEGACY] client=reticulum-php type=<peer|gateway>`.
The type is `gateway` when `mode = 6` and `peer_url` is not `https`; that is
only a hint for the log.

Legacy, any other `client` (`rns-post-interface`, `reticulum-post`, …): under
enforcement, `403 signature_required`. Otherwise a new row is inserted, as
today. An `identity_hash` key in the metadata is ignored and logged
`[REG-LEGACY … identity_claim_ignored]`. Only `rns-js` claims are honoured
(A8).

## 8. The announce guard

This guard is required (A3, A4, A6). Registration signing alone does not
close announce-replay interception. It applies to **every announce, path
responses included, received on a row whose `client` is `rns-js`, in every
mode**. It runs after `AnnounceValidator` has verified the destination hash
and the signature, and **before** `registerLocalDestinationIfOwnInterface`,
`upsertPathFromAnnounce`, announce caching and relaying.

```
I        = SHA-256(announce public key)[:16]
owner(R) = R.identity_hash                     if R.registration_proof = 'signed'
         = R.claimed_identity_hash             if R.registration_proof = 'none'
                                                  and no row has identity_hash = R.claimed_identity_hash
                                                  and enforcement is off
         = none                                otherwise
accept   ⇔ owner(R) ≠ none  and  I = owner(R)
```

An announce that is not accepted from an `rns-js` row is dropped whole: no
local binding, no path update, no announce cache, no relay. It is logged as
`[ANNOUNCE-FOREIGN] interface=<id8> dest=<hash> identity=<I8> owner=<…>`.

`owner(R)` is evaluated when the announce arrives, so a legacy row whose claim
becomes owned by a signed row loses it at once, even if it raced past §7.2
step 4.

- **Nothing legitimate breaks.** The web client registers IN destinations only
  under `IdMgr.id` (Retichat-js `app.js:5816`, `lxmf_router.js:70`, per the
  critique). Its delivery, rfed and distro announces all carry its own
  identity.
- **Browsers are endpoints.** Modes 3, 5 and 6 are refused for `client =
  rns-js` at registration, signed or legacy (`400 transit_mode_not_allowed`).
  The guard runs in every mode anyway, so an old row that already holds a
  transit mode is covered.
- **Seen announces never shorten a browser's paths.** In
  `upsertPathFromAnnounce`, the `shorter_path_replaced` branch (lower hops,
  random blob already seen) applies **only** when the receiving row is a PHP
  peer row or a gateway row (`client` `reticulum-php` or `rns-post-interface`).
  On an `rns-js` row, a seen random blob never replaces a path. Reference RNS
  refuses seen blobs outright. The exception exists for the documented
  retichat↔selectiv direct-versus-gateway case, which only transit rows
  produce.
- With the guard in place, the endpoint→endpoint overwrite in
  `registerLocalDestinationIfOwnInterface` can only move a binding between
  rows that have the same owner (two tabs of one identity, D11). The identity
  fallback in `deliverLocallyIfKnown` only ever sees rows that passed the
  guard.

## 9. The gateway

The gateway is the Reticulum-rust `PostInterface`. The Python `PostInterface`
in `python/RNS/Interfaces/PostInterface.py` MUST reach parity.

1. **Identity.** The gateway signs with its **persistent transport identity**.
   - **Rust:** `Transport::start` loads or creates `storage/transport_identity`
     before `load_system_interfaces` builds the interface. Add an accessor that
     returns the identity, and clone it once in `start_exchange_worker`,
     outside the interface lock (`process_incoming` already takes `TRANSPORT`
     inside it, so a second lock-order edge must be avoided). A missing
     identity at registration is a loud ordering error (§5 of the principles).
     It never leads to an unsigned registration.
   - **Python:** RNS 1.5.2 builds interfaces in `__apply_config` before
     `Transport.start`. On a non-transport node, `Transport.identity` is also
     replaced by an ephemeral one at every start. So `PostInterface` MUST
     itself load or create `RNS.Reticulum.storagepath + "/transport_identity"`
     with `Identity.from_file` / `Identity().to_file`, using the same file and
     format, before its first registration. `Transport.start` then loads the
     same key. It signs with that persistent key whether or not
     `enable_transport` is set. A failed registration MUST NOT abort interface
     creation (today it does, from `__init__`).
2. **Body.**
   - **Wake mode:** `client = reticulum-php`, `mode` as configured (6 in
     production), `peer_url` = the wake base URL (`wake_url` minus `/v1/wake`),
     and `peer_interface_id` / `peer_session_token` random per process, as
     today. All of them are signed.
   - **Poll mode:** `client = rns-post-interface` with `transport`.
   - The gateway fetches its challenge with its own public key.
3. **One row for good.** The row is keyed by the gateway's identity hash, so
   restarts keep the same `interface_id` and PHP-side paths survive gateway
   restarts (they do not today). `peer_url` becomes an address attribute that
   the relay wakes. The relay never calls `/v1/peers/confirm` on a gateway
   (its wake server answers 404 there).
4. **The 401 is the event** (this fixes the wake-mode wedge). On `401` from an
   exchange, the interface **stays online in Transport**, so nothing goes
   through an `[OFFLINE-DROP]` window. It immediately fetches a challenge,
   registers signed and continues the same exchange cycle with the new
   session. That happens at most once per 401: a 401 right after a fresh
   registration is logged and ends the cycle. After a relay DB reset the row
   is gone and the relay will not wake the gateway, but the gateway's next
   outbound packet (backbone announces never stop) drives an exchange, gets
   the 401 and re-registers.
5. **Failure, without timers.** A registration that fails on the network or
   with a 5xx is logged, and the interface stays online in Transport. The next
   exchange trigger (an outbound-packet signal, a wake, or the poll tick in
   poll mode) starts with a registration. Only one registration is in flight
   at a time. There is no backoff sleep: the current back-off of up to 60 s is
   removed (§3/§4 of the principles). Terminal codes (§6) stop registration
   until the process restarts.
6. **Decrypting.** The gateway decrypts `session_token_encrypted` with the
   transport identity (§5).
   - If the challenge endpoint answers `404`, it registers legacy and accepts
     a plaintext token, until enforcement (§11).
   - If a signed registration is answered without `session_token_encrypted`,
     that is a protocol error (terminal).

## 10. PHP relay peers: a one-time nonce confirmed at the peer's URL

A PHP relay has no Reticulum key; its "transport identity" is a random
`identity_hash_hex`. A peer proves the URL it claims instead. Only
`connectToPeer` on the relay at that URL can issue the nonce, and the receiving
relay confirms it **at that URL**.

A plain callback to the peer's `/v1/interfaces/exchange` would prove nothing.
Registration at the peer is open, so an attacker can obtain valid credentials
there and hand them over.

The trust anchor is the peer's HTTPS URL (WebPKI), the same anchor every peer
exchange already relies on.

### 10.1 Normalising the URL

`normalise(u)`:

1. Trim the value.
2. Strip trailing `/`.
3. Strip one trailing `/v1/wake`.

A relay's `host_url` MUST equal, after normalisation, the `node_url` its peers
configure for it. This is already required today for deduplication.

### 10.2 The initiator (`connectToPeer` toward configured peer B, URL `U_B`)

1. **Its own row first.**
   - If a URL row for `U_B` exists, keep its `interface_id` and session token:
     the re-bind happens in place, so the queue for B survives.
   - Otherwise create one now: new `Lid`, new `Ltok`, `peer_url = U_B`,
     proof `local`, status `offline`, no remote credentials.

   This MUST be committed before step 3. B may call back, or exchange with
   `Lid`/`Ltok`, before step 4 runs.
2. **Pending nonce.** Upsert `peer_registration_nonces(peer_url_hash =
   SHA-256-hex(U_B), peer_url = U_B, nonce_hex = 16 random bytes hex,
   local_interface_id = Lid)`. This replaces any earlier pending nonce for
   `U_B`, so there is at most one pending nonce per configured peer. It MUST be
   committed before step 3, and no transaction may be open during step 3.
3. **POST `U_B/v1/interfaces/register`:**

   ```json
   {"name": "<own host>", "bitrate": 1000000, "mtu": 500,
    "metadata": {"client": "reticulum-php", "peer_url": "<own host_url>",
                 "peer_interface_id": "<Lid>", "peer_session_token": "<Ltok>"},
    "registration_nonce": "<nonce_hex>"}
   ```

   `registration_nonce` is top-level, so an old relay ignores it and never
   stores it.
4. **On `200`:** store B's `interface_id` and `session_token` as the row's
   remote credentials (`peer_interface_id`, `peer_session_token`) and set
   status `online`.

   **On anything else:** log `[PEER-REGISTER] <U_B> -> <status> <error>`, delete
   the pending nonce if it is still there, and stop. The next event (§10.5)
   registers again.

### 10.3 The receiver (`registerInterface`, peer-confirmed path)

1. **Shape.**
   - `registration_nonce`: 32 lower-case hex.
   - `peer_interface_id`: 32 lower-case hex.
   - `peer_session_token`: 64 lower-case hex.
   - `peer_url`: a string.

   Anything else gets `400 bad_registration`.
2. `U = normalise(peer_url)`. `U` MUST be `https://…`, or a loopback
   `http://127.0.0.1|[::1]|localhost…` when
   `[registration] allow_loopback_http_peers = true` (staging only). Anything
   else gets `400 peer_url_not_allowed`.
3. With **no database transaction open**, POST `U/v1/peers/confirm`
   `{"nonce": "<registration_nonce>", "peer_interface_id": "<peer_interface_id>"}`
   once.
   - Success is HTTP `200` with a JSON body whose `confirmed` is `true`.
   - Anything else gets `403 peer_confirmation_failed`, logged as
     `[PEER-CONFIRM-FAIL] <U> -> <status>`.

   Because step 4 looks the row up by exact `U`, the confirm always goes to
   the URL of the row being bound: the stored URL for a re-bind, which for a
   configured peer is also its configured `node_url` (§10.1). It never goes
   to a `/v1/wake` variant or to any other URL in the body. A claim that
   matches no stored or configured URL can only create a new row (open
   peering, §16.2). It can never re-bind one.
4. **Bind.** Look up the URL row with normalised `peer_url = U` and
   `identity_hash IS NULL`.
   - If it exists, re-bind it in place: new session token, new peer
     credentials, proof `confirmed`.
   - Otherwise INSERT it with proof `confirmed`.

   Log `[PEER-CONFIRM] <U> <created|rebound> interface=<id8>`.
5. **Respond as today**, with a plaintext `session_token` (§5).

The register request together with its nested confirm is one network action
under §1: it MUST finish within 5 s. The initiator asserts this, and logs a
late success as a §1 violation. The initiator needs a second PHP worker to
serve the confirm while its own request waits on the receiver. PHP-FPM on the
production hosts has one. Staging and the tests run `php -S`, which needs
`PHP_CLI_SERVER_WORKERS ≥ 2`. The `/v1/wake` handler already depends on this
kind of nesting.

### 10.4 `POST /v1/peers/confirm`

```json
{"nonce": "<32 hex>", "peer_interface_id": "<32 hex>"}
```

The relay consumes the nonce atomically:

```sql
DELETE FROM peer_registration_nonces WHERE nonce_hex = :nonce AND local_interface_id = :id
```

- `rowCount() = 1`: `200 {"confirmed": true}`.
- Otherwise: `403 {"error": "unknown_nonce"}`.
- Malformed: `400 {"error": "bad_confirm_request"}`.

The endpoint reveals nothing else. Knowing the nonce is the whole proof.

The state is bounded with no clock:

- one row per configured peer URL;
- a confirm deletes its row;
- the next `connectToPeer` replaces it;
- `/v1/initialize` deletes rows for URLs that are no longer configured;
- `clearAllData()` empties the table.

`created_at` is stored for operators. Nothing compares it with a clock.

### 10.5 Events that drive peering (no hourly clock)

- **Maintenance.** `ensureConfiguredPeerSessions` connects a configured peer
  that has **no row, or a row without remote credentials**. Its existing
  throttle window still applies. The `peer_session_heal_after_seconds` rule
  (3600 s offline) is removed. A merely offline peer never triggers a
  re-registration. `peer_session_self_heal_test.php`'s heal-after assertion is
  replaced by one that pins this.
- **The 401 event.** `exchangeWithPhpPeer` logs every non-2xx as
  `[PEER-HTTP] <url> -> <status> <error>`; `httpPostJson` must return the
  status, not `null`. A `401` is the event to re-register:
  - If the row's URL is a configured peer, call `connectToPeer` **once**,
    skipping the liveness check. The 401 is the proof that the session is
    dead. The exchange is not repeated in that request: the next wake drives
    it.
  - If the URL is not configured, log `[PEER-401-UNCONFIGURED]` and mark the
    row offline.
- **A wake from an unknown waker.** A relay that receives `POST /v1/wake
  {"waker_url": W}` and has no URL row for `W` logs `[WAKE-UNKNOWN-PEER] <W>`.
  Then, if the body does not carry `"session_lost": true` and `W` passes the
  §10.3 step 2 scheme rule, it sends **one** fire-and-forget wake to `W` with
  `{"waker_url": "<own host_url>", "session_lost": true}`.
  - A wake that carries `session_lost` is never answered with another wake,
    so the reflection happens once and cannot loop.
  - The relay that receives it runs its ordinary wake handling. The hint is
    not trusted: only the authenticated exchange's `401` triggers
    re-registration.

### 10.6 Recovery

| Event | What happens |
|---|---|
| Initiator DB reset | Maintenance finds no row and connects. B confirms at A's URL and re-binds its row in place, so B's queue and paths survive. |
| Receiver DB reset, both sides configured | B's maintenance finds no row and connects. |
| Receiver DB reset, only A configured | A's next wake reaches B, which has no row and wakes back with `session_lost`. A pulls from B, gets `401`, and re-registers once. B confirms and inserts the row. |
| Secret or nonce table lost mid-registration | That registration fails with a status, and the next event registers again. |
| README "Rotating a PHP peering's credentials" | Unchanged: `DELETE` the initiator's row, then `/v1/initialize`. The initiator creates a new `Lid`/`Ltok` (proof `local`) and a nonce. B confirms and re-binds in place. `peer_session_rotation_test.php` must run its nodes with `PHP_CLI_SERVER_WORKERS=2`. |

## 11. Rollout

### 11.1 Configuration

```toml
[registration]
enforce_signed_registration = false   # James flips to true on a date he sets
allow_loopback_http_peers   = false   # staging only: true
```

While enforcement is off ("accept-both"), every path in this spec is live:
signed registrations are preferred, and legacy registrations are accepted and
logged `[REG-LEGACY] client=<c> type=<t>`. With enforcement on:

- unsigned registrations get `403 signature_required`;
- unconfirmed peer registrations get `403 peer_confirmation_required`;
- `authenticateInterface` answers `401` for every row whose proof is `none`,
  so each remaining legacy session re-registers properly or is refused;
- the announce guard's legacy branch ends.

**Enforcement is gated on the date James sets, not on `[REG-LEGACY]` going
quiet.** An attacker, or the selectiv Aug-01 `app.js` that keeps reappearing,
can keep that log busy forever. Before flipping, read `[REG-LEGACY]` grouped by
`client`. Any `reticulum-php` or `rns-post-interface` line there is a gateway
or a peer that would be cut off.

### 11.2 Deploy order

Each phase is gated by the existing checks: `deploy.sh` runs the whole PHP
suite, then `verify-live-stamp.sh`; the web has its boot gate, CSP check and
`verify-deploy.sh`.

| Phase | What | Notes |
|---|---|---|
| 0 | Staging only (`staging.sh`, `STAGING_PHP=local`, gateway in wake mode, `PHP_CLI_SERVER_WORKERS=2`) | The §15 before/after stage MUST fail on 3281ad5 (and on Reticulum-rust before its change) and pass on the fix. |
| 1 | Relays, accept-both: selectiv, then retichat.com | Everything except enforcement. Before Phase 2, probe the schema on both nodes: the columns and the UNIQUE index exist. A failed MySQL `ALTER` leaves the fingerprint unrecorded and would make every signed registration 500. |
| 2 | Retichat-js | New page loads sign. Against a relay still on Phase 0 code, the client gets a `404` from the challenge endpoint and registers legacy. |
| 3 | Gateway: James pushes Reticulum-rust and redeploys (`rnsd-redeploy.sh`) | It registers signed and gets an identity row. Its `interface_id` changes this one time and is stable from then on. Check rx/tx per minute (runbook §5). Once paths have moved, James deletes the legacy bridge row: `DELETE FROM interfaces WHERE interface_id = '<legacy id>' AND registration_proof = 'none'`. Python bridges follow the same path. |
| 3b | PHP peering | Once both relays run Phase 1 code, run the README rotation procedure once. The peering then rests on `local` + `confirmed` rows and is closed to A5. |
| 4 | Enforcement, on James's date: selectiv, then retichat.com | A config edit on each host. |

### 11.3 What old software experiences

| Phase | Old cached tab | Old gateway binary | Relay without this code (peer) |
|---|---|---|---|
| 1–3 | Works unchanged through the legacy path. One exception: if the same identity has a signed row on that relay (the user also opened a new tab), its re-registration gets `403 identity_requires_signature` and its announces are dropped. The "down" text says to reload. | Works unchanged (legacy, `[REG-LEGACY] type=gateway`). | Registers without a nonce, so it takes the legacy path. It is refused only for a row that is already `local`/`confirmed` (`403 peer_confirmation_required`). |
| 4 | Its next exchange gets 401 (`none` row) and its re-registration gets `403 signature_required`. It shows "down … reload" and, being old code, tries again every 5 s until reloaded. | Refused, and the bridge is down. **Phase 3 must be finished first.** | Refused, and the peering is down. Both relays must run this code first. |

### 11.4 Client fallback

A client falls back to legacy registration only on a challenge `404` (§2.5).
Once every relay it talks to enforces, a later client release MAY remove the
fallback. A forged `404` would need someone on the path inside HTTPS.

### 11.5 Rollback

- **A relay back to 3281ad5:**
  - The new columns are ignored, and signed rows' `metadata_json` carries no
    identity, so nothing breaks.
  - New browsers get `404` from the challenge endpoint and register legacy. The
    old relay inserts a fresh row for them.
  - Gateways do the same.
  - Peers lose the confirm and fall back to the old peer_url re-bind.

  **This restores A1, A3–A8.** The hotfix keeps A2 closed.
- **Enforcement back off:** flip the switch. It takes effect at once.
- **Web, before Phase 4:** any build works. **After Phase 4:** the rollback
  target MUST be a build that signs.
- **Gateway, before Phase 4:** any build works. A legacy registration
  inserts a separate legacy row, because identity rows are invisible to URL
  lookups. **After Phase 4:** the rollback target MUST be a binary that signs.
- **A relay rolled back to old code while its peer runs this code:** the old
  relay's registrations without a nonce are refused at the peer's `local` or
  `confirmed` row. Delete that row on the peer (one statement), or roll both
  relays back.
- **Schema:** the changes are additive, so a rollback needs no schema change.
  Old code never writes `identity_hash`, so the UNIQUE index never conflicts.

## 14. Test vectors

The vector file contains:

| Section | Contents |
|---|---|
| `relays.A` / `relays.B` | `relay_secret` for each relay. Every vector is presented to A. |
| `identities` | `browser`, `gateway` and `other`: private key (`x25519_prv || ed25519_seed`, RNS layout), public key and identity hash |
| `challenges` | the MAC input, MAC and challenge bytes for every challenge used, including relay B's and one minted for another identity |
| `registrations` | four end-to-end positive vectors: `browser-first` (seq 0 → 1, INSERT), `browser-reregister` (seq 1 → 2, non-ASCII name), `gateway-wake` (`reticulum-php`, mode 6, peer fields, seq 5 → 6) and `gateway-poll` (`rns-post-interface`, `transport`). Each one has the request body, the field-by-field `lp` breakdown, the signed bytes, the signature, the expected identity hash and new seq, a response example, and an encrypted token pinned by a fixed ephemeral key and IV (with the shared key, derived key, HMAC key and AES key for debugging) |
| `negative` | fourteen vectors, each failing exactly one §4.3 step: a tampered name, bitrate, `peer_url` or `peer_session_token`; another key's signature; a replay after success (wrong seq); a lower-seq challenge; **relay B's MAC**; a challenge for another identity; a forged seq inside a challenge; a mismatched `metadata.identity_hash`; an unsigned metadata key; a browser asking for mode 6; an upper-case public key |
| `tokens_negative` | a flipped ciphertext bit, and decryption by the wrong identity. Both MUST fail to decrypt. |

How the file was checked when it was committed:

- **RNS 1.5.2:** `.venv/bin/python Reticulum-post/tools/registration_vectors.py --check`.
  `Identity.validate` accepts every signature, `Identity.hash` matches every
  identity, and `Identity.decrypt` recovers every pinned token.
- **PHP sodium/openssl:** `php Reticulum-post/tools/check_registration_vectors.php`
  (150 checks). It re-derives keys, MACs, signed bytes and pinned tokens, runs
  a reference §4.3 verifier over all eighteen registration vectors, and
  decrypts every token.
- **Retichat-js** `lib/rns/identity.js` under Node (24 checks), and
  **Reticulum-rust** `identity.rs` (20 checks). Both cross-checks ran on
  2026-10-03 from scratch scripts that are not committed here. The
  deterministic Ed25519 signature is byte-identical across RNS, the web
  library, Rust and sodium. Each library decrypts every pinned token and
  refuses both token negatives.

Each implementation MUST pin these vectors in its own test suite:

## 16. Residual exposure and decisions still open

1. **Transit registration is open.** Anyone can register a gateway-class row:
   signed with their own identity, or legacy before enforcement (`client`
   `reticulum-php` or `rns-post-interface`, mode 6). Such a row keeps the
   seen-blob `shorter_path_replaced` exception (§8), so a hop-lowered replay
   through it still pulls paths. It can also name any URL as `peer_url` and
   so draw wakes there. Closing this needs a decision on **who may register a
   transit row**: for example, a relay config listing the gateway identity
   hashes allowed one, with PHP peers limited to configured URLs. This spec
   does not decide it.
2. **Open peering.** The confirm proves that the registrant controls the URL
   it names. It does not say whether the relay wants that peer at all
   (POST-Reticulum direction). That is a separate decision.
3. **Outbound calls to URLs the registrant chooses.** The confirm (§10.3) and
   the wake-back (§10.5) send one small, fixed POST to a fixed path on an
   `https` URL the registrant named. Each is 1:1, with no amplification, and
   the wake-back never chains. The wake-back is new protocol and needs
   James's OK.
4. **Accept-both is open by design.** Until enforcement, a victim who has
   never signed on a relay (only old tabs) can still be taken over there
   through the legacy path (A1 against a `none` row). The announce guard
   already confines what a legacy row can bind to the identity it claims.
5. **Restoring a DB backup** brings back an old `relay_secret` together with
   old `seq` values. Each captured body in that range can then be replayed
   once. The replayer gets an encrypted token it cannot use, so the cost is
   one session eviction per captured body.
6. **Two devices sharing one identity:** the last registration wins (D11),
   unchanged. The 409 step stops a race from spinning.
7. **Gateway after a failed registration** (§9.5): the next outbound packet,
   wake or poll drives the next registration while the interface stays online
   in Transport. This was the design's open question, and James has only said
   "re-register on the 401". Confirm the rest.
